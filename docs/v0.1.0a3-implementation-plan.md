### Frozen scientific boundaries

CorpusTrail is responsible for discovery, retrieval, exact identity/canonicalization, deduplication, evidence acquisition/trust, broad-topic corpus membership, human review, review-order prioritization, Knowledge assertions, provenance, maintenance and ASReview export.

ASReview remains responsible for active-learning screening for a particular systematic/scoping-review question. Broad-corpus membership is not downstream eligibility. ASReview labels do not automatically become reference labels or broad-corpus decisions.

Priority changes review order only. It never excludes candidates or provides a stopping rule. Model/classifier output is an observation, not automatically scientific truth. Producer and authority remain separate. History, original evidence and earlier assessments remain auditable.

The next phase should add a researcher-facing application layer over the existing services—not replace the provenance-first backend.

At the original inspection, both release targets were unchanged and the worktree was clean. No files, dependencies, tags or remote state were changed, and no external provider/model calls were made. Two offline reproductions and 12 focused curation regression tests passed. That inspection was not a rerun of the entire release-acceptance suite.

### Concrete findings retained from the original audit

**The five-complete/zero-recorded situation is real.** Five complete review drafts produced zero recorded scientific review events. Draft completion validates the form; it does not record a decision.

**Authoritative recording currently changes membership immediately, per paper.** A new Finish Review boundary is a new workflow policy—not merely a button rename. Existing sessions and events must retain their meaning. The approved deferred-publication policy applies to new guided sessions only.

**Discovery preview/execution mismatch is explained by fresh planning.** `SearchPlan` identity includes its creation timestamp. The CLI creates a new plan for each invocation, so identical query/run inputs at different times can produce different plan IDs. The service already accepts an exact supplied plan; the UI should persist and execute the same plan. See [discovery service](https://github.com/Rickk-B/CorpusTrail/blob/ffd657fcc92a683722cf052cfc01695c66056b24/src/corpustrail/discovery/service.py).

**The current review UI is reusable infrastructure, not a suitable application shell unchanged.** Its localhost binding, Host/Origin checks, CSRF token, CSP, restrained JSON endpoints and method-blind allowlisting are valuable. Embedded HTML/JavaScript and the fixed-session handler should be separated before project-wide expansion. See [review HTTP implementation](https://github.com/Rickk-B/CorpusTrail/blob/ffd657fcc92a683722cf052cfc01695c66056b24/src/corpustrail/curation/http.py).

**Existing sessions freeze evidence and configuration.** Better evidence acquired later does not update an existing packet. Configuration changes can invalidate session operations. The new UI needs explicit continuation/new-snapshot workflows, not silent evidence replacement or relaxed guards.

**The displayed broad-corpus question currently derives from the project name.** Configuration supports a review scope, but new guided sessions should freeze and display the actual corpus definition. Old packets must not be rewritten.

**Find best legitimate evidence needs an honest capability boundary.** The built-in Europe PMC full-text resolver requires a known PMCID. No general standalone DOI/PMID-to-PMCID enrichment service was found. The initial UI can compose existing acquisition capabilities but cannot promise unsupported automatic enrichment.

**The model service implements structured assertion extraction.** Its output schema is not a membership-assessment schema. Corpus classification should share safe invocation infrastructure while retaining a separate typed task/output contract. Do not force assessments into authoritative review events or disguise classification as scientific extraction.

**Method-blindness must be enforced in API responses.** Hiding provider names or scores in CSS is insufficient. General paper-detail responses must not be reused indiscriminately inside blinded review.

**A navigation action must not manufacture a scientific judgment.** The existing domain supports `unresolved`, but new guided UI sessions should offer the three approved scientific outcomes. Skip for now records navigation/workflow state only; it must not append an unresolved scientific ReviewEvent merely to advance.

### Existing service and storage boundaries

- `Project.create/open/configure/upgrade/status` use explicit project roots. Bootstrap configuration remains immutable; configuration revisions append events with concurrency guards.
- Scope changes after authoritative reviews are guarded. The UI must not silently redefine the topic or reinterpret earlier labels.
- Database reads are read-only; writes use transactions. Open/status do not implicitly migrate projects. Upgrades are explicit and backed up.
- Existing migrations 001–037 remain frozen. Later persistence changes must be additive, with numbers assigned during implementation.
- Discovery preserves provider observations separately from canonical papers and retains requests, failures, pagination, aliases and exact identity evidence.
- Canonical metadata is selected by existing rules; alternatives and field provenance remain inspectable. Do not add arbitrary provider precedence in the UI.
- Identity is mint-once and exact-identifier based. Model-generated identity is not a trusted enrollment capability. Title similarity is not authoritative identity evidence.
- Evidence separates metadata, abstracts, structured/document representations and pending/invalid/mismatched artifacts. Evidence availability has no membership implication.
- Review sessions preserve frozen packets, draft/navigation history and scientific review-event links. Authoritative writes use policy and stale-history checks.
- Priority snapshots preserve eligible human label event IDs and cutoff/availability. Insufficient labels are not negative training examples. Ranking retains the entire population.
- Knowledge assertion authority is purpose-specific and separate from producer. Knowledge validation must not become a shortcut around the corpus review service.
- Model configuration/status/connection testing and explicit extraction exist, but real OpenAI-compatible server interoperability has not been demonstrated. No particular hosted service or local runtime is validated by the mock tests.
- ASReview exports use current authoritative members, unlabelled bibliography and stable IDs. Downstream results remain question-specific and do not change membership.

## 3. Proposed local application architecture

### Layering

```text
Local launcher / future desktop wrapper
                  ↓
Packaged researcher-facing browser UI
                  ↓
Versioned loopback HTTP API
                  ↓
Application/workflow services and paginated read views
                  ↓
Existing scientific services + new versioned population/reference/assessment services
                  ↓
Immutable records, source artifacts, evidence and auditable lineage
```

The application/workflow layer coordinates services without becoming a second scientific authority system. The HTTP layer translates requests and errors; it does not decide science.

### Proposed package boundaries

```text
corpustrail/
  application/       # Dashboard, catalogue, project and workflow commands
  local_app/         # Loopback server, versioned routing, security, packaged assets
  populations/       # Origin-independent immutable candidate populations
  references/        # Versioned Known in-scope / Known out-of-scope collections
  classification/    # Plans, assessments, policies, context selection and audit
  imports/           # Future optional format adapters, not Checkpoint 1 work
```

These are proposed modules, not existing capabilities. Final names can follow existing package conventions during coding review. Core does not depend on import formats, model SDKs, UI frameworks or optional ML engines.

### Application responsibilities

- Project dashboard and configuration forms.
- Paginated catalogue and readable paper details.
- Persisted discovery-plan preparation and exact execution.
- Evidence acquisition/enrichment orchestration, within actual capabilities.
- Candidate-population selection and version inspection.
- Known in-scope / Known out-of-scope management and provenance.
- Guided review operations, completion and explicit publication.
- Classification planning, context inspection, results and audit.
- Existing Prioritization, Knowledge, Models and Export presentation.

Scientific logic remains below HTTP:

- Identifier normalization, identity resolution and deduplication.
- Canonical metadata selection.
- Evidence identity verification and trust.
- Review validation and membership projection.
- Reference eligibility, versioning and context selection.
- Classifier input/output validation, provenance and policy application.
- Training-label eligibility and ranking.
- Assertion validation and purpose-specific authority.
- Export selection and downstream identity mapping.

The browser and HTTP handlers must not construct SQL, shell out to CLI commands as their normal backend, infer authority, implement independent membership rules or bypass evidence trust.

### Pages and navigation

| Section | Main purpose |
|---|---|
| Project / Dashboard | Corpus definition, membership and work progress, active jobs, useful next actions |
| Discovery | Search concepts, exact frozen plans, network confirmation and results |
| Papers / Corpus | Readable catalogue, population/collection filters and paper details |
| Evidence | Availability, acquisition/enrichment attempts, limitations and pending identity |
| Curation | Method choice, populations, reference collections, sessions, assessments and audit |
| Knowledge | Assertions, evidence, producer, validation, conflicts and lineage |
| Models | Optional adapter configuration, credential status, locality and explicit connection testing |
| Export | Preview, frozen export, downstream question identity and exact result mapping |

Proposed routes use project/session/population handles internally, for example `/projects`, `/p/{handle}/dashboard`, `/papers`, `/papers/{paper_handle}`, `/curation/references` and `/curation/runs/{run_handle}`. Researchers navigate by readable names and paper cards, not copied IDs. Handles resolve to exact canonical identity; titles never become identity join keys.

Paper cards show title, authors, year, journal/source, exact identifiers where available, discovery/import sources in operational views, evidence status and separate review/membership/assessment status. Raw provider records appear only in an advanced provenance view.

### API shape and large-collection contract

Proposed resources include projects, paper catalogue/details, jobs, search plans/runs, evidence workflows, population versions, reference versions, reference-selection manifests, review sessions, assessment runs and exports.

- Version the HTTP contract, initially `/api/v1/...`; serialized scientific contracts have their own versions.
- Return paginated records with cursor, total/count semantics, sort/filter description and snapshot/version identity.
- Use stable tie-breakers such as canonical paper ID for deterministic ordering.
- Bound a response page, not the total logical collection size.
- Define filters and sorting server-side. Do not fetch all papers into JavaScript and filter locally.
- Keep large manifests/artifacts behind streaming/download endpoints or paginated inspection.
- Reject stale cursors/revisions clearly when a live view changes; versioned population/reference views remain stable.
- Aggregate counts server-side against an identified snapshot. Avoid returning giant arrays of IDs as routine status output.
- Add documented resource limits for individual payloads, processing chunks, runtime and disk use without imposing an arbitrary scientific collection-size cap.

### Server, privacy and future desktop packaging

Approved approach: packaged HTML/CSS/JavaScript, a thin standard-library loopback server and application services. No heavyweight desktop framework is selected.

A later one-command launcher can open/register a project, start the backend, open the browser and manage port conflicts/shutdown. A future desktop wrapper starts the same server/API. Desktop installers are not Checkpoint 1 work. Eventual target order is macOS, Windows, with Linux compatibility preserved.

Safeguards:

- Loopback-only binding, strict Host/Origin validation, CSRF protection and CSP.
- Server-registered project roots; no arbitrary HTTP file paths, SQL or shell execution.
- Confined artifact access, explicit file selection and safe downloadable filenames.
- No remote frontend assets, scripts, fonts or telemetry by default.
- No credentials in browser storage, URLs or response objects.
- Redacted, actionable errors and restrained request logging.
- No network activity merely from launching, opening a project or reading a page.
- Scientific text rendered as data, not executable HTML or model-supplied commands.
- Method-blind endpoints use separate allowlisted data models, not merely CSS hiding.

Do not promise that a local model is private solely because it has a loopback endpoint. Preserve the existing explicit locality declaration and safeguards; a local server can itself relay content.

## 4. Project configuration and broad-corpus definition

### Guided creation

The wizard collects:

- Project name and topic description.
- Explicit broad-corpus definition/question.
- Discovery providers and search concepts.
- Evidence resolver choices.
- Reviewer pseudonym and authority role.

It generates technical identifiers/revisions and calls existing configuration services with stale-revision checks. Researchers do not edit versioned JSON or assign themselves authority implicitly by opening the UI.

Credential configuration contains environment-variable names only. Existing model and discovery credential namespaces remain separate. No bespoke secret manager or shared API account is introduced. Environment setup guidance can be shown without accepting/storing a secret in ordinary project forms.

### Definition versioning

Population/classification/reference/review plans must identify the broad-corpus definition version and configuration provenance. A definition version can initially be derived from the existing scope/config event plus a content hash, rather than introducing a competing definition truth table unnecessarily.

New guided review packets display the actual frozen definition. Historical packets retain their existing question and scope. Existing post-authority scope-change restrictions remain in force; redefining a corpus after authoritative curation requires a later explicit migration/review policy, not a convenient settings edit.

Changing unrelated configuration during an active session must not silently relax current guards. Initially provide explicit restart/continuation with preserved earlier work. Any narrower invalidation rules need their own reviewed compatibility change.

## 5. Generic candidate-population abstraction

### Equal workflow origins

Discovery-first:

```text
Configured discovery
→ immutable source observations
→ exact canonicalization/deduplication
→ evidence acquisition/trust
→ candidate-population version
→ manual or assisted broad-corpus curation
```

Corpus-first, future import implementations:

```text
User-supplied corpus/source records
→ preserved import source and normalized observations
→ the same exact canonicalization/deduplication services
→ the same evidence acquisition/trust services
→ candidate-population version
→ the same manual or assisted broad-corpus curation
```

Classification must depend on a population/evidence snapshot, not on whether the source was discovery or import. There is no separate import-only classifier.

### Population version contract

Each immutable version preserves:

- Population ID/version and project ID.
- Parent version(s) and creation actor/timestamp.
- Canonical member paper IDs, deterministic order/manifest hash and count.
- Explicit selection rule and source snapshot/cutoff where applicable.
- Origins: discovery run IDs, imported source versions/records, existing collection versions or explicit researcher selection.
- Paper-to-origin lineage retaining every contributing observation.
- Union/deduplication rule and exact identity state used at freezing.
- Included/excluded source-selection changes, with reasons where supplied.
- Contract/software/configuration version.

Do not duplicate bibliography or entire evidence text in every membership row. Link to canonical records and separately frozen representations. Candidate membership and effective broad-corpus membership are different dimensions.

Supported origin types are conceptually:

- One or multiple discovery runs.
- One or multiple imported sources.
- An existing CorpusTrail collection/corpus snapshot.
- A researcher-selected subset.
- A deterministic combination/union of the above.

New discovery or import results create a new population version; they do not append invisibly to a population used by an earlier run. Combining origins yields a unique canonical-paper population while preserving all raw source observations and their many-to-one links.

The initial abstraction operates within a project. Cross-project combination requires explicit identity import/mapping later; matching titles or independently minted IDs is not sufficient.

### Evidence and identity evolution

Population identity and evidence snapshot are separate. Acquiring a new abstract/full text need not change the set of canonical candidates, but a new assessment must freeze a new evidence snapshot if it uses that evidence.

If later exact identity resolution merges or remaps papers, earlier population IDs and results remain historically interpretable. Record explicit lineage and create a successor population; do not rewrite earlier manifests. Unresolved identity conflicts remain visible and cannot silently enter an exact-mapped assessment population as resolved papers.

### Import architecture, not current implementation

Future import adapters may support user-provided PubMed/OpenAlex/provider exports, Scopus/Web of Science exports where permitted, Zotero/EndNote exports, RIS, BibTeX and CSV/TSV. This is an extension direction, not a claim that these formats are currently supported.

An import adapter produces source records, not membership judgments:

1. Preserve the source artifact/hash, declared format, adapter/version and import identity.
2. Stream/iterate records and preserve record locators, raw metadata and normalization failures.
3. Call existing identity/canonicalization services with exact supported identifiers.
4. Preserve identity conflicts, aliases, duplicates and source-to-paper links.
5. Expose imported evidence as untrusted until the appropriate trust/identity checks succeed.
6. Freeze a candidate-population version with import lineage.

Import does not itself perform network retrieval. Later lookup/acquisition is separately planned and authorized. A provider-exported open-access flag does not establish document trust. Imported inclusion/exclusion columns do not automatically establish broad-corpus labels or reference truth.

Bulk import should use durable chunks and stable record locators, retain partial failures and be replay-safe. A failed import does not roll already preserved source observations out of history; a finalized population must distinguish complete versus explicitly accepted partial source processing.

No import formats are implemented in Checkpoint 1. The a3 baseline establishes origin-independent contracts; a production bulk importer remains separately scoped unless explicitly approved later. Synthetic imported-source observations can test the contract without pretending a user importer exists.

### Population selection UI

Longer-term choices:

```text
Candidate population
○ Papers discovered by CorpusTrail
○ Import an existing corpus
○ Existing CorpusTrail collection
○ Combined population
```

Show only implemented actions as enabled. An unimplemented Import action is labelled unavailable/planned, not a nonfunctional promise. Version previews show source counts, unique papers, duplicate observations and identity warnings without loading the entire population in the browser.

## 6. Large versioned reference collections

### Researcher-facing model

The primary logical collections are:

- **Known in-scope**.
- **Known out-of-scope**, optional.

They are folder-like UI collections, not literal filesystem folders. Do not call them correct/incorrect papers. Borderline/near-miss is an optional annotation/context, not a third automatic binary reference label.

The UI may recommend a small initial set, but the domain and storage have no arbitrary application-level upper limit. Five, fifty, five hundred, several thousand or larger collections are valid subject to explicit practical resources. Bounded model input and paginated UI responses are not reference-set size limits.

### Reference label records

Each assignment preserves:

- Stable assignment ID and exact canonical paper ID.
- Label: in-scope or out-of-scope.
- Assigning actor/producer type, identifier and version where relevant.
- Human attestation and its source event where applicable.
- Rationale/boundary annotation where supplied.
- Evidence available/used at assignment time, with representation IDs/hashes.
- Broad-corpus definition/version.
- Source artifact/record or imported annotation lineage.
- Timestamp, availability/validation state and supersession/correction relation.

An imported or model-proposed label is not silently human-attested or authoritative. The engine eligibility policy must identify which label sources may be used. The normal default should use explicitly human-established broad-corpus examples; other sources remain distinguishable and require explicit eligibility/attestation, not agreement with a model or manifest.

Known labels used as references are not automatically corpus membership events. Conversely, a current authoritative membership can be deliberately added as a reference with its exact event lineage, rather than silently populating a reference collection.

### Reference-set versions

A version preserves its ID, parent(s), definition version, creation actor/time, eligibility policy, current label-assignment membership and content manifest/hash. Old assignments and versions are never edited.

Researchers can:

- Add papers to either collection.
- Remove papers from a successor version.
- Correct/move a paper between collections through new assignment/version events.
- Inspect who assigned a label, when, using what evidence and under which definition.
- Commit a batch of proposed edits as one new immutable version.

Version creation uses a revision guard to prevent concurrent lost corrections. Unsaved UI selection/edit proposals are not a classifier-usable frozen version.

An effective reference version should not silently contain the same canonical paper as both in-scope and out-of-scope. Preserve contradictory source assignments, flag them and require explicit resolution/eligibility selection before using that paper as a binary reference. Do not delete either historical assignment.

### Scalable persistence proposal

Use normalized per-paper membership/assignment records and deterministic manifests, not one routinely fetched JSON array. Immutable versions may use chunks/content-addressed membership segments or an auditable change stream plus a frozen resolved-state manifest. Do not physically copy full evidence for every version.

Materialized indexes/projections are rebuildable administrative accelerators, not independent scientific truth. A version's exact effective members must remain recoverable, deterministic and integrity-checked. Avoid both uncontrolled full snapshot duplication and an unbounded delta chain that makes ordinary queries impractical.

The precise SQLite layout should be selected in the reference checkpoint after realistic synthetic measurements. Collection size is constrained by measured resource availability, not a hard-coded ten-paper design or arbitrary thousand-paper cap.

### Iterative correction loop

```text
Reference set v3 → assessment run A
              ↓ researcher inspection/audit
Add 7 Known in-scope + 4 Known out-of-scope assignments
              ↓ explicit version commit
Reference set v4 → explicitly requested assessment run B
```

Run A continues to point exactly to v3. Run B points to v4. New versions do not silently retrain an engine, rebuild a model into an old identity, rerun classification or replace earlier results.

From any operational assessment/audit view, offer Add to Known in-scope / Add to Known out-of-scope with explicit label attestation and provenance. Correcting an assessment, assigning a reference label and authorizing membership are separate actions. The UI may offer them together as explicit choices but cannot infer one from another.

This loop is identical for discovery-derived and imported candidate populations. It preserves old assessments, models, indexes and selected contexts.

## 7. Bounded reference selection and derived representations

### Full collection versus execution context

A classifier run identifies the full reference-set version, but an invocation need not receive every paper. Large collections must be represented/retrieved intelligently, not concatenated into a prompt.

Examples of explicit strategies:

- Complete eligible reference set for a local trained classifier.
- Complete local embedding index with selected nearest examples.
- Nearest 12 in-scope and nearest 6 out-of-scope examples, if configured.
- Learned global topic representation.
- Global profile plus selected positive/negative examples.

The numbers are examples of configurable context budgets, not hard-coded collection limits or default scientific policies.

### Versioned selection strategy

Preserve:

- Strategy ID/version and configuration/hash.
- Full reference-set version and eligible role/source policy.
- Input/target evidence snapshot and representation rules.
- Retrieval/index artifact ID, content hash and source version.
- Embedding/feature/model identity, version, normalization and preprocessing.
- Ranking/similarity metric, tie-breakers, seeds and approximate-search parameters where applicable.
- Per-label quotas, diversity rules, filters and self-match/duplicate exclusion policy.
- Context/token/resource budgets and truncation rules.
- Missing-representation handling and retrieval failures.
- Global profile/summary dependencies and producer provenance.

The reference-selection component is separate from the assessment engine. It can be shared across compatible engines without changing membership semantics.

### Per-assessment context manifest

Every assessment using selected/derived context must link to an immutable manifest identifying:

- The complete reference-set version.
- The precise selected paper IDs and label assignment IDs.
- Retrieval ranks/scores and selection decisions.
- The exact representations/passages supplied, with versions/hashes and locations.
- Included reference labels and their provenance.
- Derived profiles/summaries actually supplied, with their content/hash and lineage.
- Excluded/omitted selections and budget reason where relevant.
- The assembled model/task input hash and safely preserved exact input artifact.

A strategy description such as nearest examples is not enough. The actual subset/context must be recoverable even if a later index produces different neighbors. Preserve the output of nondeterministic/approximate selection, not only its algorithm name.

Sensitive source text stays in confined project artifacts, not giant browser responses or unredacted logs. Context inspection/download is explicit; exact payload preservation and minimization must be compatible.

### Derived profiles and summaries

Derived information carries its own producer, version, source dependency hashes, generation settings and validation state. It is not reference truth merely because it summarizes human-labelled references. Model-produced summaries remain non-authoritative and require authorization if generated remotely.

Creating new profiles/indexes is a deliberate job. New references produce new derived artifacts; they do not overwrite artifacts used by earlier runs. Core supports these provenance contracts without running LLM summarization or installing an embedding model in this phase.

### Leakage and consent safeguards

- Held-out validation labels/answers must not enter retrieval indexes, prompts or profiles used to assess that held-out set.
- Exclude the target paper and exact duplicates from example retrieval by default for independent evaluation; record any deliberate operational self-reference policy.
- A labelled reference population overlap can be useful operationally, but cannot be counted as independent validation without an appropriate split.
- Only explicitly selected reference labels/examples may be supplied as classifier input. This is distinct from leaking hidden human judgments into blinded evaluation.
- Remote transfer consent covers candidate evidence, selected reference evidence, selected labels, topic profiles and task/definition text actually transmitted.
- Connection-test consent never authorizes scientific or reference-context transfer.
- Changed reference selection/evidence/payload requires a new plan/consent; no silent expansion to full text or all references.
- No undeclared provider/model fallback when context exceeds a limit. Fail, abstain or replan explicitly.

## 8. Discovery and bounded evidence enrichment

### Exact search plans

Proposed operations: `prepare_search`, `inspect_search_plan`, `execute_search_plan`, `inspect_search_run`.

Preparing a search creates one immutable saved plan. Run search executes that exact plan/hash; it does not reconstruct a fresh timestamped plan. The confirmation shows providers, exact query text, request/result limits, what leaves the machine and execution scope.

A changed query, configuration or budget requires a new plan and confirmation. Preserve current run-ID reservation, completed replay and interrupted-execution safeguards. Do not change old SearchPlan hashing casually to make UI IDs look stable.

Multiple providers produce a parent workflow with distinct frozen provider plans. Partial failures remain visible; there is no silent provider substitution. Run-specific catalogue populations follow observation-to-canonical links, not the current CLI's project-wide canonical list.

### Find best legitimate evidence

The high-level workflow should:

1. Inspect current trusted evidence and exact aliases.
2. Explain the bounded identifier-lookup/acquisition plan and supported limitations.
3. Obtain explicit network confirmation for the identified operations.
4. Perform only eligible exact-identifier lookups if implemented.
5. Handle identity conflicts explicitly before trusting new aliases.
6. Freeze/revalidate resolver plans against accepted identifier state.
7. Attempt configured eligible resolvers.
8. Preserve every attempt, raw response/artifact, normalization and outcome.
9. Refresh readable evidence status without changing membership.

If enrichment is not implemented, say so: the current resolver may require an identifier that is unavailable. Do not imply a completed search for all possible evidence when only one configured route was attempted.

### Exact-identifier enrichment contract

Design lookup requests independently of provider adapters:

- Project/paper ID, verified input identifier and exact normalization.
- Provider/adapter/version and supported lookup operation.
- Configuration, timestamp, request limits/retry policy and explicit transfer basis.
- Request/response hashes and source record locator.
- Returned identifiers and their relationship/status semantics.
- Exact evidence connecting returned identifiers to the input paper.
- Acceptance, conflict, unsupported or unresolved outcome.

DOI/PMID/verified provider ID may establish PMCID or another supported identifier only where a legitimate provider supplies an exact record relationship. Preprint/publication/version identifiers must not be treated as interchangeable merely because a provider returns both.

Conflicting owners or bibliographic/document identity evidence route to the existing explicit identity-resolution boundary. Fuzzy title matching never establishes canonical identity, PMCID or document identity.

Use existing providers where their actual lookup contract can be safely supported. No provider expansion or unsupported API promise is part of the plan. A concrete lookup adapter requires offline recorded/synthetic tests and separate scoped implementation review.

### Evidence states

Readable badges distinguish metadata, abstract, verified structured/full-text evidence and pending/invalid/mismatched artifacts. Retrieval availability and scientific evidence sufficiency are different dimensions.

Pending PDFs remain unavailable as trusted review/model evidence. Missing abstracts, failed retrieval or resolver exhaustion never imply exclusion. Do not bypass paywalls or use questionable acquisition routes. New evidence does not silently update a frozen review packet or assessment.

## 9. Approved guided review redesign

### Scientific outcomes and Skip for now

New guided review sessions offer:

- Include.
- Exclude.
- Insufficient evidence.

Skip for now is navigation/workflow state, not a fourth scientific outcome. It appends no scientific membership judgment, does not label a reference example and does not erase an existing decision. A previously unreviewed paper remains undecided; if a paper already has authoritative membership, skipping a new review does not reset it.

The existing unresolved domain state remains readable for historical records and other explicit workflows. Do not rewrite old unresolved events or introduce Defer as a new guided scientific outcome.

Insufficient evidence records an actual human judgment, with required rationale and evidence/review extent according to the existing contract. Skip means no judgment was made. UI counts and provenance distinguish them.

### Paper layout

```text
Paper information and frozen broad-corpus definition
→ trusted evidence / availability and pending warnings
→ Include / Exclude / Insufficient evidence
→ evidence reviewed and rationale
→ Previous / Skip for now / Save & Next
```

The final paper offers Finish Review. Optional sticky navigation must not obscure evidence or decision fields. Record human decision is not a separate normal per-paper UI action.

### Drafts and Save & Next

- Autosave preserves drafts and never changes membership.
- Save & Next flushes pending edits, validates the form/evidence extent, records a non-authoritative human review observation and advances only after success.
- Navigation/skip with an incomplete draft preserves its draft; it must not imply that the paper has a saved scientific review.
- Editing a saved review creates a new observation on the next explicit save; earlier observations remain.
- Use command IDs and expected revisions to make retries/double-clicks safe.
- Show Unsaved, Saving, Saved or Needs attention; keep ledger terminology in advanced provenance.
- Preserve entered text and provide recovery after stale revisions or failed autosave. Do not let a rejected JavaScript promise permanently poison later navigation.

### Finish Review and summary

Finish validates the selected saved review events, exact population/evidence snapshot and session state. It shows counts of Include, Exclude, Insufficient evidence, skipped/undecided and incomplete drafts.

Incomplete drafts are not silently converted to insufficient judgments. The UI offers explicit return/fix or preservation as undecided. A workflow can be closed with skipped cases if the summary clearly says they remain undecided; this is not a claim that every candidate received a scientific assessment.

A completion receipt records the session/population versions, selected review-event IDs, skipped/undecided cases, evidence/configuration snapshots, actor/time and publication outcome. Membership publication selects only explicit valid saved judgments, never skipped cases.

### Separate authoritative confirmation

Approved for newly created guided sessions:

```text
Decision + rationale
→ Save & Next: non-authoritative human review observation
→ Finish Review: validation and summary
→ Confirm corpus updates: explicit authority-bearing publication, if permitted
```

For non-authoritative completion:

> Your review has been saved. Corpus membership has not changed.

For authoritative publication:

> These confirmed decisions updated broad-corpus membership.

The confirmation identifies the exact selected changes, including insufficient-evidence states, and the reviewer exercising configured authority. No authority is inferred merely from UI access or producer type.

### Publication transaction and lineage

The publication plan freezes:

- Session/completion revision and selected non-authoritative human event IDs.
- Candidate population and exact evidence snapshot.
- Corpus definition/configuration revision.
- Current authoritative membership heads and relevant decision-history guards.
- Authorized actor, policy and intended state changes.
- Command/publication ID and content hash.

One transaction rechecks all guards, creates new human authority-bearing events with appropriate current-membership supersession, adds explicit links to the saved review events and writes the publication receipt/replay result.

- A failed publication must not partially update membership.
- An identical completed retry returns the same result, without new events.
- The same command ID with different content is rejected.
- Competing/stale decisions require inspection/replanning and new confirmation; no automatic overwrite.
- Model or reference labels are never published merely because they agree with saved reviews.
- Human approval of an assisted assessment preserves its assessment/evidence lineage separately from the original model producer.
- Existing `supersedes` semantics for membership events must not be overloaded to mean an unrelated model/reference source link; add explicit linkage where necessary.

Existing historical sessions retain immediate per-paper authority semantics where that was their contract. The legacy `corpustrail review serve` remains available and is not silently reinterpreted. New guided sessions use a versioned lifecycle/publication policy.

### Completion and continuation

Offer View corpus, Review undecided/uncertain papers, Find missing evidence, Continue discovery, Export and Return to dashboard. There is no dead-end final paper.

Later corrections create new events. Better evidence leads to an explicit successor session/snapshot with lineage, not alteration of the evidence supporting an old event.

## 10. Generic classifier and run contract

### Separate assessment, review and membership

1. Classifier assessment: non-authoritative engine observation.
2. Human review: explicit human judgment under the broad-corpus definition.
3. Membership authorization: separate authority-bearing confirmation establishing current membership.

Neither a classifier score nor Knowledge validation bypasses the review authority service. Exclude assessments never delete candidates, hide them from audit or remove their historical observations.

### Engine interface

```text
describe()             → engine identity/version, capabilities, locality
prepare(request)       → immutable typed assessment plan
assess(plan/chunk)     → typed assessments or preserved per-paper failures
```

The engine receives explicit frozen inputs and no direct capability to change membership, human authority, identity, evidence trust, prioritization state or ASReview eligibility.

The interface supports lazy/chunked inputs and typed bounded execution units. It does not require loading an entire collection or supplying every reference in one request.

### Frozen run inputs

An assessment run freezes:

- Run/project ID and contract version.
- Candidate-population version and manifest/hash.
- Broad-corpus definition/configuration version.
- Reference-set version and eligibility policy.
- Evidence snapshot/version and representation hashes.
- Engine/adapter/model configuration and software/version.
- Classifier policy and calibration version, or explicit absent/not calibrated state.
- Reference-selection/retrieval strategy and derived/index dependencies.
- Locality and transfer/consent plan where applicable.
- Chunk/request/resource budgets and timestamp.

Conceptually:

```text
Assessment run
= engine
× candidate population
× reference set
× evidence snapshot
× policy/configuration/calibration
× reference-selection strategy
```

A change to any scientifically relevant input creates a new run identity. Evidence, reference or population changes never silently rewrite earlier results.

### Normalized assessment fields

| Field group | Required meaning |
|---|---|
| Identity | Assessment ID, run ID, canonical paper ID, population version |
| Assessment | Include, exclude or uncertain, independently of human membership |
| Sufficiency | Separate evidence-sufficiency status, including insufficient/unknown as appropriate |
| Score | Optional value, score type, meaning and calibration identity; no invented probability |
| Explanation | Rationale, evidence support, uncertainty and limitations |
| Evidence | Actual representation IDs/versions/hashes and locations |
| References | Full reference-set version and exact selected-context manifest |
| Engine | Type/version, provider/adapter/version, configured and reported model identifiers |
| Policy | Definition, configuration/settings, classifier and calibration versions |
| Execution | Timestamp, locality, usage metadata, success/failure and ambiguity |
| Authority | Non-authoritative by default; later human authorization links are separate |
| Lineage | Parent/child assessments, selection/index dependencies, corrections and authorization |

Missing abstract must not imply exclude. Uncertain and insufficient evidence are not negatives. A failed request is not an uncertain scientific assessment unless the engine actually produced one; preserve failure separately.

Output validation rejects unknown identifiers, unsupported schema fields, evidence outside the plan and attempts to claim human authority. Model responses are untrusted data: no code execution, shell commands, arbitrary file reads, URL following or tool access.

### Storage and Knowledge relationship

Store typed immutable assessments and lineage, with deterministic content/provenance identity. Exact replay is idempotent; independent runs with the same value remain distinct. Preserve contradictory assessments and explicit invalid/rejected outputs safely where appropriate.

Do not physically duplicate assessments into a second truth store merely for uniform API shape. Knowledge views may adapt assessments read-only with their original producer and non-authoritative status. A model-produced scientific Knowledge claim still uses existing assertion machinery; membership assessments do not become authoritative Knowledge facts or corpus decisions.

### Human authorization

An authorized human can review a frozen selection of assessments and explicitly confirm decisions under a policy. That creates human review/authorization events linked to exact assessment and evidence. The original engine producer is unchanged. Current membership guards and atomic publication apply.

Default a3 uses human-reviewed publication. Automatic threshold-based publication, model-only authority policies and stopping rules are outside scope.

## 11. Engine integrations and explicit hybrid graphs

### Modes and implementation status

The architecture supports:

```text
How should CorpusTrail assess broad-corpus membership?
○ Manual only
○ Local embedding classifier
○ External LLM
○ System One / typed decision model
○ Hybrid
```

Manual is always functional without optional dependencies. Other choices are enabled only when an implementation/capability has actually been installed and separately approved. Planned/unavailable modes must not masquerade as working engines.

| Mode | Integration design | Boundary/status |
|---|---|---|
| Manual | Existing review service plus approved guided lifecycle | No classifier installation or model required |
| Local embedding | Optional engine with versioned local feature/index/model artifacts, full-set training/retrieval where appropriate | Separate implementation gate; no automatic downloads; similarity is not calibrated inclusion probability |
| External LLM | Existing safe model invocation infrastructure plus a separately versioned membership task/schema and reference-context plan | Separate gate; exact remote consent; real-server compatibility remains unvalidated |
| Typed decision model | Generic capability-based adapter for typed/bounded input/output | Separate gate; Jev is a potential later plugin, not a required dependency or validated backend |
| Hybrid | Explicit versioned orchestration graph with child assessments and routing events | Separate gate; no hidden fallback or false single-model provenance |

Do not hard-code Jev, OpenAI or another model/provider into core curation or Knowledge schema. Model settings, task specification and engine implementation remain separately versioned.

### External adapter reuse

The existing model service is task-specific to scientific assertions. A later membership engine can share transport, credentials, input hashes, consent, reservations and diagnostics, but needs a distinct typed assessment capability. Keep structured assertion extraction behavior unchanged during that adaptation.

Models remain optional. Users supply their own credentials. No shared key, credential discovery, paid call, named-server validation claim or real scientific invocation is introduced by this planning phase. MCP remains separate and out of scope.

### Hybrid graph provenance

Example future graph:

```text
Candidate + frozen population/evidence
→ local embedding assessment
→ explicit policy routing
→ ambiguous cases: typed model
→ remaining uncertainty: LLM or human queue
```

Alternative future graph:

```text
Full reference-set version
→ versioned local retrieval index
→ selected positive/negative context manifest
→ bounded typed/LLM assessment
→ human audit/review
```

Preserve graph ID/version, node implementations, routing predicates/policy/calibration, request budgets, transfer boundaries, every child output/failure, selected context and resulting parent assessment.

No silent substitution after a child fails. A changed provider/model/graph requires a new identity and consent where relevant. Node outputs remain assessments even for clear cases. Human routing is a pending review task, not a synthetic model judgment.

UI labels identify hybrid origin and expose the contributing stages. Do not claim a single model produced an assessment generated by multiple engines.

## 12. Calibration, audit and result views

### Score semantics

Distinguish:

- Similarity score.
- Learned classifier probability.
- Model-reported confidence.
- Calibrated probability.

Do not treat these as interchangeable or assume a meaningful threshold of 0.5. Policies preserve explicit include/uncertain/exclude bands where supported, score direction, calibration version and what happens when no calibration exists.

High-recall policies are important because false negatives in corpus construction are costly. A high-confidence exclude remains an assessment, not deletion, authoritative exclusion or a stopping rule.

### Validation boundary

- Keep reference/training, calibration and held-out evaluation roles explicit.
- Preserve exact human label source/event IDs, semantic scope, cutoff and availability.
- Do not silently use insufficient-evidence cases as negative labels.
- Do not automatically import ASReview eligibility labels as broad-corpus references.
- Freeze evaluation populations/protocols before scoring, and do not tune/report on the same held-out outcomes.
- Reference-selected held-out examples must be excluded from training/context where independence is required.
- Later correction versions are valid development information for new runs, but repeated testing on the same corrected test set is not fresh independent validation.

Report recall on known inclusions, precision/specificity where estimable, uncertain/insufficient fractions, disagreements and audit outcomes with denominators. Tiny sets and sparse negatives do not establish reliable exclusion policies. Training-set agreement is not validation.

### Audit sampling

False-negative auditing must be easy. Provide random and policy-stratified audit samples from likely out-of-scope, uncertain and disagreement groups as well as likely in-scope cases.

Freeze audit selection IDs, population/run versions, filters, strata, random seed and selected paper IDs. Preserve sample outcomes. Do not report a biased convenience sample as an unbiased performance estimate without appropriate qualification/weighting.

Audit corrections can create human reviews and optional reference assignments; these are explicit actions with separate lineage. An audit run never deletes unsampled candidates.

### Operational result presentation

Show separate concepts:

- Likely in-scope.
- Likely out-of-scope.
- Uncertain.
- Evidence insufficient.
- Engine disagreements.
- Human-reviewed.
- Human-authorized membership.
- Failed/not assessed, so failures do not disappear from counts.

Assessment bands, sufficiency, disagreement and human status can overlap. Define count semantics and provide a mutually exclusive primary assessment/failure breakdown separately from overlay filters; do not double-count overlapping panels as a total population.

Illustrative UI, not measured results:

```text
Classification results
Likely in-scope       2,418
Likely out-of-scope  21,604
Uncertain               795

[ Review uncertain ]
[ Audit likely in-scope ]
[ Audit likely out-of-scope ]
[ Inspect disagreements ]
```

Candidates labelled exclude remain in the project and accessible through filters/audit. Do not hide the low-ranked tail, automatically remove excluded assessments from future populations, or treat review completion as proof of corpus saturation.

Corrections may offer Add to Known in-scope / Add to Known out-of-scope. A new reference version is previewed and explicitly committed. A new run is explicitly requested; nothing silently retrains or reruns.

### Blinded versus assisted workflows

Method-blind API responses omit classifier/model scores, ranks, assisted assessments, retrieval provider/query/arm details and prior judgments where the policy requires it. Advanced provenance for a blinded session must not provide an alternate route to the omitted information.

Operational assisted review may show suggestions only when explicitly selected. It must clearly distinguish a model suggestion from human membership. Manual blinded validation and operational assisted curation are different workflow modes and endpoint allowlists, not CSS toggles over the same rich payload.

## 13. Large-corpus processing and durable jobs

Design for hundreds, thousands and tens of thousands of candidates/references without requiring all records in browser memory. This is architecture preparation, not an a3 claim of million-paper performance.

### Processing rules

- Page/filter/sort catalogue, populations, references and assessment results server-side.
- Use stable cursors/versioned snapshots and bounded response sizes.
- Iterate/chunk import, index preparation, context selection and assessment.
- Persist per-item or per-chunk progress and explicit failures.
- Keep manifests and large evidence in confined artifacts/normalized stores, not repeated API blobs.
- Preserve fixed run population; current project growth does not change an active run.
- Record processed/succeeded/failed/not-attempted counts against exact population identity.
- Use practical concurrency limits and short database transactions; network calls must not hold a project write transaction open.
- Do not perform full database integrity scans or whole-population joins on every UI poll.
- Add indexes/read projections only when justified; they remain rebuildable and do not reinterpret source truth.
- Resource/budget exhaustion produces visible partial/interrupted state, not silent truncation or exclusion.

### Job lifecycle

Planned → Awaiting authorization → Running → Completed / Partial / Failed / Interrupted.

The job coordinator wraps existing service logs and reservations. It does not replace request provenance or silently change replay rules.

Cancellation stops between safe units. An uncertain external request outcome must be inspected; no implicit resend. Local processing can resume from verified chunks. A run retry/recovery preserves completed results and uses documented replay or a new linked run, depending on the backend's contract.

### Reference/resource constraints

No arbitrary collection cap. Individual model context, per-request payload, configured budget, disk, RAM and compute constraints are explicit. If a full-set engine cannot fit resources, report that limitation or require a different strategy; do not silently drop references.

Indexes/profiles can be shared by immutable dependency identity across runs, without being mutated after a version change. Browser status reports counts and progress, not complete reference/example contents.

- Partial jobs/failures stay visible; interruption does not silently trigger repeat external calls.
- Read operations remain side-effect free and deterministic for a fixed snapshot.
- Frozen migrations remain unchanged; old projects open as before or use explicit backed-up additive upgrade.

### Scale and UI tests

- Paginated candidate/reference/result APIs never require full browser-memory loading.
- Stable sorting/filtering handles duplicate titles and missing metadata.
- Thousands of synthetic references and tens of thousands of catalogue candidates exercise contracts without an arbitrary collection cap.
- Performance measurements state the environment; this is not a universal throughput guarantee.
- Chunked job resume retains progress and failures without duplicate scientific writes.
- Autosave errors, tab/revision conflicts and retry-after-response-loss preserve work.
- Bottom navigation, final summary and follow-up actions have no dead ends.
- Model status distinguishes installed/configured/credential present from real connectivity.
- Availability labels do not imply unimplemented engine/import functionality.

### Security and privacy tests

- Loopback, Host/Origin, CSRF, CSP and safe rendering protections remain.
- No arbitrary file reads, path traversal, SQL/shell execution, model-directed tools or unsafe deserialization.
- Shared XML policy applies to supported encodings and parser entry points.
- No credentials in configuration, browser storage, status, errors, logs or provenance.
- Remote consent is bound to actual candidate/reference/profile context and exact input hashes.
- Local operations do not trigger external calls; model/provider opening/status is read-only.
- Blinded APIs omit protected methods/prior labels/scores, including alternate advanced routes.
- Public product fixtures/docs retain project-level identity and no private research/real credential material.
- Model responses remain untrusted structured data and cannot request arbitrary follow-up actions.

### Packaging and compatibility

- Full standalone suite and focused new tests on Python 3.11, 3.12 and 3.13.
- Core installation without ML, ASReview or model SDK dependencies.
- Optional ML tests and unchanged prioritization semantics.

- Existing offline tutorial and exact ASReview temporary round-trip where part of acceptance.

Browser automation may be approved as a development-only dependency during implementation; no dependency is added by this planning task. Later macOS/Windows packaging needs platform acceptance, not an assumption that Linux tests prove installer readiness.

## 17. UX acceptance workflows

### A. Discovery-first five-paper acceptance

Use synthetic, non-scientific fixtures with six observations resolving to five canonical papers:

- One paper returned by two providers.
- One DOI-missing paper.
- Similar-looking titles that remain distinct.
- One verified structured-text paper.
- Two abstract-best papers.
- Two metadata-only papers, one with a pending PDF.

All requests use local/recorded fixtures; no external network, account or credentials are required.

Workflow:

1. Launch the local application and create/open a project.
2. Define the broad corpus and configure fixture providers/resolvers through forms.
3. Preview the exact search and Run search; assert identical plan identity.
4. Inspect five readable catalogue cards and retained duplicate source observations.
5. Request legitimate evidence; inspect verified/pending/unsupported outcomes honestly.
6. Choose Manual only, without optional ML/model dependencies.
7. Review with bottom navigation and Save & Next.
8. Skip a paper temporarily; assert no scientific event/reference label/membership change, then return and review it.
9. Close/reopen mid-session and resume without lost drafts or duplicate observations.
10. Save two Include, two Exclude and one Insufficient evidence judgments.
11. Finish Review and inspect the exact summary.
12. If authorized, separately confirm corpus updates.
13. Return to the dashboard; view corpus, acquire more evidence, continue discovery or export.

Authority variants:

- Non-authoritative: five saved human observations, all five initially unreviewed memberships unchanged.
- Authoritative: membership unchanged before confirmation; afterward two included, two excluded and one insufficient.
- Skipped-case variant: finish with an explicitly undecided paper; it receives no judgment and is absent from published decision changes.

Verify duplicate clicks/retries, stale competing membership, unchanged pending evidence, strict blinded response allowlists and export of the two authoritative members without question-specific labels.

The researcher does not edit JSON, copy paper IDs, interpret giant payloads, understand PMCID plumbing/ledger terminology or use the terminal for ordinary in-app workflow. A one-command launcher may remain the installation bridge; desktop installers are later work.

### B. Corpus-first longer-term acceptance

This is a future functional acceptance target, not a claim that import/real engines are part of Checkpoint 1 or already implemented. Contract-level tests can use synthetic imported-source observations now.

1. Launch and create/open a project; define broad scope.
2. Choose Import an existing corpus when an approved importer is available.
3. Stream a synthetic large export through source preservation and exact canonicalization.
4. Inspect imported counts, duplicate observations, identity issues and partial failures.
5. Resolve evidence where supported without implicitly trusting imported PDFs or labels.
6. Create/manage large Known in-scope and optional Known out-of-scope collections.
7. Freeze the candidate-population/reference/evidence versions.
8. Choose an installed separately approved engine and inspect its configuration/context plan.
9. Authorize remote transfer if applicable; run explicit chunked assessment.
10. Inspect likely in-scope, uncertain, evidence-insufficient and disagreement groups.
11. Audit likely out-of-scope papers easily; all remain accessible.
12. Correct errors through human review and optionally add/move reference labels.
13. Commit a new reference-set version; inspect old assignments and provenance.
14. Explicitly request reassessment with the new reference version, not an automatic rerun.
15. Publish selected human-confirmed judgments if authorized, using atomic stale-guarded confirmation.
16. Return to dashboard/export; downstream ASReview labels remain separate.

Use a configurable synthetic corpus at a tens-of-thousands scale for later resource tests, not a scientifically meaningful labelled dataset. Test a large reference collection without all references entering browser memory or bounded model prompts. Exact workload size and resource expectations are documented per test environment.

### C. Combined-origin and iterative lineage acceptance

Combine a discovery run, a synthetic imported source and an existing collection. Exact duplicate IDs collapse to one candidate while every observation/source remains.

Freeze population P1/reference v3/evidence E1 for run A. Add new candidates to P2 and correct references into v4. Run A must still resolve exactly to P1/v3/E1 and its original selected-context artifacts. Run B explicitly uses its chosen P2/v4/evidence snapshot.

Reopen and compare the runs without rewriting A. Check that auditing/correction works identically for both source origins, and that a model exclude never deleted or hid a paper.

### D. Bounded-context and privacy acceptance

Using offline deterministic engines only:

- Create a reference collection larger than a bounded engine's context.
- Freeze a configured positive/negative selection strategy.
- Verify actual selected paper IDs, assignment IDs, representations, ranks and input hashes.
- Change an index/strategy/reference version and ensure the old context remains recoverable.
- Verify held-out labels and excluded self-examples never appear in evaluation context.
- Require consent for the exact remote-declared mock payload, including selected reference material; local-declared tests need no external consent.
- Confirm malformed output/failure cannot mutate membership or authority.

This validates architecture/safety, not real-server interoperability or scientific classifier performance.

## 18. Scope exclusions, risks and remaining decisions

### Explicitly outside the first checkpoint

- Source/domain changes, authority redesign or migration creation.
- Classifier engines, reference-set persistence or corpus import implementation.
- Model calls, remote provider calls or paid usage.
- Dependency additions, desktop installers or framework selection.
- Tagging, pushing, releasing or retagging public releases.

### Outside the a3 baseline unless separately approved

- Production real embedding/LLM/typed/hybrid engines.
- Broad multi-format import coverage and provider expansion.
- Unattended scientific extraction, historical research import or ontology expansion.
- Automatic ASReview seeds, automatic exclusion or stopping.
- MCP, cloud/collaborative infrastructure and public deployment work.
- Heavyweight desktop packaging or unsupported privacy/performance claims.

### Architectural concerns introduced or sharpened

1. Large immutable versions can amplify storage. Use per-record/chunk manifests and rebuildable indexes while preserving exact resolved states.
2. A bounded engine's selected context is a scientific input. Strategy names alone are insufficient; actual inputs must be retained, with privacy-safe access.
3. Iterative correction can contaminate validation. Separate roles/splits and avoid reporting repeatedly corrected test sets as independent evidence.
4. Imported source labels can have incompatible scope. Preserve them without silently making broad-corpus references or authority.
5. Exact identity can evolve. Successor populations and explicit mappings preserve old run interpretation; never silently rewrite frozen IDs.
6. Reference labels and membership authority are distinct. Known collections require label provenance/eligibility, not authority inferred from a folder-like UI.
7. Atomic guided publication is an explicit new workflow. Preserve historical per-paper semantics and use transactional retry-safe lineage.
8. Large jobs have interruption/resource costs. Partial outcomes and safe recovery must be visible; no background implicit network repeats.
9. Overlapping assessment/sufficiency/human-status views can mislead counts. Separate primary totals from overlay filters.
10. Future desktop environments differ in paths/process/credential environments. Keep packaging-neutral interfaces and retain Linux compatibility without claiming current macOS/Windows installer support.

None of these concerns requires weakening provenance, identity, evidence trust, authority or the ASReview boundary. They require explicit contracts and carefully staged persistence/workflow implementation.

### Decisions before Checkpoint 1

No new scientific/product decision is needed before the recommended read-only Checkpoint 1. Authority timing, a3 baseline, UI approach, reference/population requirements and desktop priorities are approved.

The remaining prerequisite is the user's explicit approval of this revised plan and permission to begin Checkpoint 1. No implementation begins automatically.

Later checkpoints will need scoped implementation choices, such as an initial import format set, optional embedding implementation/dependency/resource policy, a bounded model validation protocol and any development-only browser test tooling. Those choices do not block the read-only foundation and must not be made implicitly now.

The necessary architectural direction remains a researcher-facing application/workflow layer plus explicit immutable population/reference/assessment contracts—not simplified scientific truth, hidden automatic exclusion or weakened audit history.

## 19. Approved addition — distribution, removal and storage ownership

This section adds the user's post-Checkpoint-1 development/distribution requirements.
Sections 0–18 above remain unchanged as the original approved specification and
audit context; their planning-only status statements describe that earlier revision.
Checkpoint 1 is now implemented on the development branch. This addition does not
authorize Checkpoint 2, a push, tag, GitHub Release, PyPI publication or desktop work.
It does not change any scientific, review, evidence-trust or authority semantics.

### 19.1 Development build distribution, separate from releases

**Implementation direction:** GitHub Actions downloadable artifacts, not wheel
binaries in Git history. After separately approving a checkpoint commit/push,
the existing acceptance workflow can build its exact checked-out commit. Upload
is gated on the complete Python 3.11–3.13 acceptance matrix and clean installation
tests of the actual uploaded wheel. The artifact's name and companion receipt
preserve full source commit/tree identity, development package version, run/attempt,
wheel checksum, build environment and validation results. No credentials or real
scholarly-provider/model calls are required. Public a1/a2 tags are untouched.

The wheel retains its standard pip-compatible filename; its enclosing artifact
name and receipt distinguish commits sharing an alpha `.dev` version. Installation
must not rely on package version alone to distinguish checkpoints. Exact same-source
builds are not promised byte-identical merely because source identity is preserved.
The receipt is traceability, not a signed attestation or a stable/public release.

The first receipt must separately record the preserved Checkpoint 1 implementation
commit `6e116118f05e53ec3694c60e9171cb873a437bf8` and the exact subsequent CI/distribution
source/build commit. It must never describe the wheel as built directly from the
implementation commit when its build source is the follow-up commit. Verify
ancestry and unchanged application source for this CI-only follow-up.

Download usability: GitHub sign-in/read access is required; requested 90-day
retention is bounded by repository limits. Save copies/receipts locally before
expiry. A separately approved development prerelease could later address anonymous
or long-lived downloads, but is not chosen/created implicitly. No automatic a3 or
PyPI release is allowed. See `docs/developer/DEVELOPMENT_BUILDS.md` for exact workflow,
approval and download details.

### 19.2 Ownership is independent of who generated/downloaded a file

| Category | Meaning | Removal boundary |
|---|---|---|
| A — Application software | Installed package/CLI, packaged frontend/schema, later desktop bundle | Environment/package or normal OS application removal |
| B — Application-owned state | Explicitly enrolled global settings, disposable cache/logs/temp, app registry metadata, optional downloaded runtime/model assets and rebuildable indexes | Separate scoped cleanup; never infer ownership from directory/name alone |
| C — Researcher-owned material | Projects and their scientific stores, originals/imports, external Zotero libraries, externally located documents | Preserved by default; project removal requires additional explicit confirmation; external originals are not automatically removed |

Project databases, immutable observations, acquired evidence, review history,
authority events, ranking/training snapshots, Knowledge assertions, model outputs,
reference/population versions, scientific derived summaries and exports remain
researcher-owned data. They do not become disposable cache because software created
or downloaded them. Project configuration and reviewer rights are research state,
not global app preferences. Resetting app settings must never change them.

Current implementation: projects use explicit researcher-chosen directories;
the new read-only browser creates no global application settings/cache/log store
or persistent browser storage. No storage manager, deletion endpoint or uninstall
command is implemented by this addition.

### 19.3 Future storage-location contract

**Proposed implementation, not new directories created now:** centralize platform
path/ownership policy behind a storage service, separate from scientific services
and HTTP. Never derive global storage from the source checkout/current directory.
Preserve macOS first, Windows second, Linux compatibility:

- macOS: platform-conventional `~/Library/Application Support/CorpusTrail`,
  `~/Library/Caches/CorpusTrail` and `~/Library/Logs/CorpusTrail` as distinct purposes.
- Windows: explicit per-user application directories, normally below
  `%LOCALAPPDATA%/CorpusTrail`; do not assume roaming/shared data or fixed drive names.
- Linux: respect XDG config/data/cache/state locations and their normal per-user
  defaults; no requirement for an extra runtime dependency is implied here.
- Temporary files: dedicated confined task locations with ownership/lifecycle
  metadata, not sweeping the OS's general temporary directory.
- Optional assets/indexes: distinguish downloadable/rebuildable resources from
  source/representation/assertion artifacts and record version/hash/ownership.
- Projects: explicit chosen locations, separate from disposable application data;
  do not put projects under an uninstall-owned application-state root by default.

An application project-location registry is navigation metadata, not ownership or
authority over everything beneath a path. User-selected project roots must be
protected even if they overlap an application-owned path; cleanup must fail closed
or preserve them, never assume all descendants are disposable. Unknown/unregistered
material is preserved. Losing/resetting the registry must not license broader deletion.

No plaintext secrets in global preferences, logs, cache or browser storage. Existing
user environment/credential stores remain outside ordinary cleanup. Paths revealed
through a future local Storage screen are private local information, not data to
include in public artifact/build provenance.

### 19.4 Future normal removal experience

```text
Remove CorpusTrail

✓ Application
✓ Settings
✓ Cache
✓ Logs
✓ Downloaded optional assets

□ Also permanently delete CorpusTrail research projects
```

Default application removal retains projects. Selecting project removal requires
a separate confirmation naming the exact selected projects/locations, consequences,
backup/recovery options and whether deletion is truly permanent. Do not substitute
a generic uninstall checkbox for that confirmation. Do not delete imported originals,
external Zotero libraries or external documents simply because a project references them.

Later desktop software uses the operating system's normal install/removal mechanisms.
macOS application-bundle removal and other OS uninstallers may leave user data;
optional application-state cleanup must be an honest explicit UI/platform operation,
not an unsupported claim that the OS removes all state automatically. Do not implement
a CLI that uninstalls/deletes its own running Python package. Any later privileged
helper or installer integration requires a scoped platform-safety review.

### 19.5 Future Settings → Storage & Data

Design the application service/UI boundary to accommodate these actions later:

1. Show application-data location.
2. Show project locations and ownership categories independently.
3. Clear cache.
4. Clear temporary files.
5. Remove selected downloaded optional assets.
6. Reset application settings without resetting project config/authority.
7. Delete selected project, strongly confirmed.
8. Delete all CorpusTrail application data, **excluding projects/external originals**.
9. Delete all explicitly registered/selected CorpusTrail projects, with strong
   population confirmation and backup choices; not a filesystem-wide discovery sweep.

The UI asks a narrow service to plan the exact affected ownership/path population,
shows that plan, then separately authorizes execution. HTTP must not take arbitrary
deletion paths or construct shell commands. Ownership guards must reject broad
roots, path traversal, unsafe symlinks, shared/external paths and changed targets.
Prefer recoverable removal where practical; label permanent removal honestly.
Long-running jobs/servers must be stopped or safely coordinated before cleanup.
Cleanup preserves partial failures, never quietly broadens scope to overcome them.

Deleting a reference/global index or downloaded model can invalidate an operational
cache or prevent replay until the exact version is restored. Preserve underlying
scientific run/provenance records and warn about that consequence. Never claim full
reproducibility after deleting unique non-recoverable scientific artifacts. Scientific
evidence/lineage deletion is not a “cache clear” action.

### 19.6 Current pip development install/update/removal

In the selected environment, installing a newer wheel replaces that environment's
previous CorpusTrail package. Checkpoint builds sharing a version require explicit
replacement, e.g.:

```bash
python -m pip install --no-deps --force-reinstall "/path/to/actual-checkpoint.whl"
python -m pip uninstall corpus-trail
```

Use the actual complete wheel filename and intended active environment. The first
command is for the current dependency-free core and leaves optional dependencies
unchanged. Pip uninstall removes the installed distribution/CLI, not project
directories, original imports, source checkouts, downloaded wheel files, shared pip
caches, whole environments or external libraries. Optional dependencies generally
remain. Wheel downloads can be removed independently. Stop running servers first.
Software downgrade/reinstallation must not be described as undoing a scientific
database migration. See `docs/user/REMOVAL_STORAGE.md` for user-facing steps.
